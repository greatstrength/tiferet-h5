# Request for Prototype: Error-Handling & b16 Alignment

**Project:** tiferet-h5
**Repository:** https://github.com/greatstrength/tiferet-h5
**Date:** August 11, 2026
**Version:** Request for Prototype
**Target Release:** `1.0.0a1`
**Target Branch:** `v1.x-proto`

> Draft status: the RFP process for this repo is being revised. Unlike a TRD, this document intentionally stays at the concept/technical level rather than an artifact manifest — precise Add/Update/Remove operations are left to whatever TRD eventually formalizes the port of this work to trunk.

## Overview
Tiferet core's "Service Error Protocol" (landed by `2.0.0b16`) reserves `TiferetError` for catalogued domain outcomes and expects infrastructural failures in `utils/`/`repos/` to surface as `ServiceError`, with their error vocabulary hosted beside the code that raises it rather than centralized in a domain error catalog. `tiferet-h5` predates this convention. Its `H5Client` utility still speaks the old idiom, and the in-flight fix for the now-deleted `RaiseError` helper lands on the wrong exception family (`TiferetError`) rather than the current one. This RFP is about bringing the whole error story for `tiferet-h5` current with core Tiferet's present error philosophy — not just patching the one broken import.

## Why This Matters
An infra utility that raises the wrong exception family breaks the contract consumers rely on: `AppSessionContext.run` (and any consumer code) only ever catches `TiferetError` for formatting/localization. A `ServiceError` is meant to surface as an unhandled infrastructural failure by design. Leaving `H5Client` on `TiferetError` means its failures get silently treated as recoverable domain outcomes instead of the infrastructure problems they actually are. This is a correctness issue, not a style nit — it's the difference between "the file doesn't exist" being catchable/localizable business logic versus a loud, unambiguous bug signal.

## Scope
This RFP covers the general shape of getting `tiferet-h5`'s error handling, hosting conventions, and surrounding scaffolding (docs, tests, dependency pin) into alignment with core Tiferet as it stands today. Broadly:
- Swap the exception family `H5Client` raises from `TiferetError` to `ServiceError`, matching how core's own infra utilities (e.g. `SqliteClient`) already behave.
- Stop centralizing H5's error vocabulary in a dedicated assets module — infra codes belong beside the code that raises them, and centralizing them was itself a pre-b16 habit worth dropping along with everything else in scope here.
- Take the opportunity, while touching every raise site anyway, to tighten up exception handling in general: don't swallow unrelated bugs under an infra error code, and preserve the original driver exception as context rather than just stringifying it into a kwarg.
- Retire error-code cruft that never had a real raiser — dead vocabulary is exactly the kind of thing that accumulates if left unaddressed across a migration like this.
- Bring the docs and test suite current with whatever the above settles into, and repin the framework dependency to something that actually reflects what's supported, rather than an open-ended range spanning a beta series full of breaking changes.

Out of scope, deliberately deferred to later alphas: actually enforcing schema consistency (that's its own conceptual unit — see the `1.0.0a2` Schema Integrity RFP), and anything from the broader v1 RFP list (performance, storage tuning, ergonomics, hardening, async) that isn't directly entangled with the error-handling migration itself.

## Where This Touches the Codebase
Conceptually, this is a single-utility migration with ripple effects on its immediate scaffolding: the `H5Client` utility itself, whatever module ends up hosting its error vocabulary going forward, the mapper layer only incidentally (one existing non-Tiferet exception worth a documentation pass, not a behavior change), the guide doc that describes `H5Client`'s error contract to consumers, the test suite that exercises it, and the packaging metadata declaring which framework version this all assumes.

## Open Questions for the Prototype
A few implementation decisions are left to whoever prototypes this, rather than dictated here:
- Exactly which PyTables exception types are worth distinguishing versus still collapsing into a general "wrap and rethrow" — enough to stop masking unrelated bugs, without over-engineering a taxonomy nobody needs yet.
- Whether the mapper-layer's plain `ValueError` (a class-authoring-time mistake, not a runtime failure) is worth converting to something more Tiferet-idiomatic, or is fine left as a documented, deliberate exception.
- The exact upper bound on the repinned dependency range — tied to how much of core's beta churn we're willing to absorb automatically versus pin down explicitly.

## Acceptance Criteria (outcome-level)
1. `H5Client` failures surface as `ServiceError`, never `TiferetError`, across the board.
2. The error vocabulary lives with the code, not in a separate catalog module — and nothing lingers there with no raiser behind it.
3. Wrapped driver failures retain their original exception as context; overly broad catches no longer mask unrelated bugs as infra errors.
4. The guide doc and test suite both reflect the above, with no stale references to retired helpers or catalog locations.
5. The declared framework dependency reflects a version actually validated against this work, and the local dev environment is capable of proving that.

## Prerequisites
The local development environment is currently running a version of Tiferet many beta cycles behind the one this RFP targets — that has to be corrected before any of the above can be meaningfully validated, not after.
