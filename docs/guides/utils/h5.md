# H5Client

**Module:** `tiferet_h5.utils.h5`  
**Alias:** `tiferet_h5.H5`

<a id="h5client"></a>
## Overview

`H5Client` is the concrete HDF5 infrastructure utility for tiferet-h5.  It extends `tiferet.utils.FileLoader` for path and lifecycle conventions while implementing `H5Service` via the PyTables API.

The underlying file handle is a `tables.File` object stored as `h5client.h5file`.  Unlike `FileLoader`, `H5Client` fully overrides `open_file()` and `close_file()` — PyTables uses `tables.open_file()`, not Python's built-in `open()`.

No `tables` (PyTables) exception ever escapes `H5Client`. Every failure is wrapped as a `ServiceError` (`tiferet.interfaces`) with the driver exception preserved as `__cause__` — never as a raw Python exception, and never as a `TiferetError`.

## Ubiquitous Language

- **Node** — any addressable location in the HDF5 hierarchy (a group, table, or array), identified by an absolute path string such as `/features/calc`.
- **Cause chaining** — every wrapped PyTables failure keeps the original exception attached via `raise ... from cause`, so `service_error.__cause__` is always the underlying `tables`/stdlib exception, never a stringified summary alone.

## When should you reach for H5Client?

| Use case | Best choice | Why it fits |
|---|---|---|
| Direct scripts, tests, one-off HDF5 access | `with H5(...) as h5:` | Zero setup, immediate access |
| Need to mock or swap storage backends later | Inject `H5Service` | Follows dependency injection; easy to test & replace |
| Persistent domain objects via `TableObject`/`NodeObject` | Use `H5Repository` + injected service | Keeps business logic clean and path-agnostic |

---

## Initialization

```python
H5Client(path, mode='a', **kwargs)
```

| Parameter | Type | Default | Description |
|---|---|---|---|
| `path` | `str \| Path` | required | Path to the HDF5 file. |
| `mode` | `str` | `'a'` | PyTables open mode. See table below. |

### Open Modes

| Mode | Behaviour |
|---|---|
| `'r'` | Read-only. File must exist and have `.h5` / `.hdf5` extension. |
| `'r+'` | Read-write. File must exist and have `.h5` / `.hdf5` extension. |
| `'w'` | Write. Creates or **truncates** the file. Use with caution. |
| `'w-'` | Write-exclusive. Fails if the file already exists. |
| `'a'` | Append / read-write. Creates the file if absent; never truncates. **Repository default.** |

Repositories should default to `'a'` to avoid silent data loss.

---

## Context Manager

`H5Client` implements the context manager protocol.  `__enter__` opens the file and returns `self`; `__exit__` flushes and closes regardless of whether an exception occurred.

```python
with H5Client('data.h5', mode='a') as h5:
    # h5.h5file is open here
    t = h5.get_or_create_table('/items', ItemDescription)
    ...
# file is flushed and closed here
```

`open_file()` and `close_file()` may also be called manually when a context manager is not appropriate, but the context manager form is strongly preferred.

---

## Validation Methods

### `verify_mode() -> None`

Validates that the configured mode is in `{'r', 'r+', 'w', 'w-', 'a'}`.  Raises `H5_INVALID_MODE` otherwise.

### `verify_file(path, mode) -> None` _(static)_

Validates the file path for the requested mode:

- Read modes (`'r'`, `'r+'`): checks `.h5` / `.hdf5` extension **and** file existence.
- Write / append modes: checks that the **parent directory** exists.

Raises `H5_INVALID_FILE` or `H5_FILE_NOT_FOUND` on failure.

---

## File-Level Operations

### `flush() -> None`

Flush all pending write buffers to disk without closing the file.  `close_file()` calls this automatically, but call it explicitly after large batch writes when you need durability before closing.

```python
with H5Client('data.h5', mode='a') as h5:
    for item in large_batch:
        item.to_row(table)
    h5.flush()
```

### `node_exists(path: str) -> bool`

Returns `True` if a node exists at the absolute HDF5 path.

```python
if not h5.node_exists('/features/calc'):
    h5.create_group('/features/calc')
```

---

## Group Operations

### `create_group(path, title='', create_parents=True) -> Any`

Create a group at `path`.  When `create_parents=True` (the default), any missing intermediate groups are created automatically.

```python
h5.create_group('/features/calc', title='Calculator Feature')
```

### `get_group(path) -> Any`

Retrieve the PyTables group object at `path`.  Raises `H5_NODE_NOT_FOUND` if the path does not exist.

---

## Table Operations

### `create_table(path, description, title='', **kwargs) -> Any`

Create a table at `path` using a `tables.IsDescription` subclass.  The parent group is created automatically if absent.

```python
from tiferet_h5 import TableObject
# ...
t = h5.create_table('/features/calc/steps', StepTableObject.get_description(), title='Steps')
```

Raises `H5_TABLE_CREATE_FAILED` on any PyTables error.

### `get_table(path) -> Any`

Retrieve the PyTables table object at `path`.  Raises `H5_NODE_NOT_FOUND` if absent.

### `get_or_create_table(path, description, title='', **kwargs) -> Any`

Return the existing table if the node exists; otherwise create and return a new one.  The recommended pattern for repository `save()` methods.

```python
t = h5.get_or_create_table('/features/calc/steps', StepTableObject.get_description())
obj.to_row(t)
t.flush()
```

### `append_rows(path, rows) -> None`

Append a list of plain Python dicts to the table at `path`.  String values are encoded to bytes automatically.  Flushes after all rows are written.

```python
h5.append_rows('/items', [
    {'name': 'Widget', 'price': 9.99},
    {'name': 'Gadget', 'price': 24.99},
])
```

### `read_rows(path, start=None, stop=None, condition=None) -> List[Dict]`

Read rows from the table at `path`.  All values are returned as Python natives (bytes decoded, NumPy scalars converted).

- Without arguments: reads all rows.
- `start` / `stop`: slice the row range.
- `condition`: apply an in-kernel PyTables condition string.

```python
# All rows
rows = h5.read_rows('/items')

# Sliced
rows = h5.read_rows('/items', start=10, stop=20)

# Filtered
rows = h5.read_rows('/items', condition='price > 10.0')
```

### `query(path, condition, **kwargs) -> List[Dict]`

Convenience wrapper around `read_rows` that applies a condition string.  Equivalent to `read_rows(path, condition=condition)`.

```python
matches = h5.query('/items', 'name == b"Widget"')
```

Note: string comparisons in PyTables condition strings compare against bytes literals (`b"..."`), not Python string literals.

### `remove_rows(path, condition) -> int`

Remove all rows matching `condition` from the table at `path`.  Deletion is performed in reverse index order to preserve stability.  Returns the number of rows removed.

```python
removed = h5.remove_rows('/items', 'name == b"Widget"')
print(f'Removed {removed} rows.')
```

<a id="compression"></a>
## Compression

Neither table nor array creation compresses data by default.  Pass a `tables.Filters` instance to opt in -- `tiferet-h5` does not wrap individual `Filters` options (`complib`, `complevel`, etc.) as its own parameters; construct the native PyTables object directly and pass it through.

### Tables

`Table` is a chunked PyTables leaf and natively supports compression -- pass `filters` to `create_table()` or `get_or_create_table()`:

```python
import tables

filters = tables.Filters(complevel=5, complib='zlib')
t = h5.create_table('/items', ItemTableObject.get_description(), filters=filters)
```

### Arrays

A plain `Array` (what `create_array()` produces when `filters` is omitted) is contiguous and non-chunked, and **cannot** be compressed at the HDF5 level. When `filters` is given, `create_array()` transparently creates a chunked `CArray` instead:

```python
import numpy as np
import tables

filters = tables.Filters(complevel=5, complib='zlib')
h5.create_array('/measurements/temperatures', np.array([22.1, 23.4, 21.9]), filters=filters)
```

Omitting `filters` preserves the original plain-`Array` behavior exactly -- this is fully backward compatible.

**Cost tradeoff:** compression trades CPU (on every write and read) for disk footprint. It's worth it for large, long-lived, or rarely-rewritten datasets; skip it for small or write-once/read-once tables and arrays where the CPU cost outweighs the negligible disk savings.

<a id="compaction"></a>
## Compaction

HDF5 never shrinks a file in place after `remove_rows()` -- freed row slots leave the file exactly as large as before the deletion. `compact()` reclaims that space by copying the file's live contents into a fresh rewrite and atomically replacing the original with it, wrapping PyTables' `File.copy_children(recursive=True)` (the same recursive-copy machinery behind the `ptrepack` command-line utility) rather than the higher-level `File.copy_file()` -- every leaf already carries an explicit `Filters` instance once created, and `copy_file()`'s own `filters` kwarg only supplies a *default* for leaves that don't have one of their own, so it silently declines to actually change compression on existing leaves.

### `compact(filters=None) -> None`

```python
with H5Client('data.h5', mode='a') as h5:
    h5.remove_rows('/items', 'price < 1.0')
    h5.compact()
```

`compact()` can be called from inside a normal `with H5Client(...) as h5:` block without any special handling -- internally it closes the file handle, atomically replaces the original file with the compacted rewrite, and reopens it in the same mode before returning, so `h5` remains usable immediately afterward.

Pass `filters` to also apply (or change) compression during the same rewrite -- since compaction is already a full-file copy, this is the natural point to introduce or update compression settings on an existing file:

```python
import tables

h5.compact(filters=tables.Filters(complevel=5, complib='zlib'))
```

Raises `H5_COMPACT_FAILED` if the copy or the atomic file replacement fails.

**Cost tradeoff:** compaction is a full-file rewrite -- its I/O cost scales with total file size, not with how much was deleted. Reach for it after a churn-heavy sequence of deletions (or before archiving a file long-term), not after every individual `remove_rows()` call.

<a id="streaming-reads"></a>
## Streaming Reads

`read_rows()` and `query()` both materialize their full result set as an in-memory list before returning -- fine for small tables, but a table large enough that HDF5 was chosen for in the first place can make that a real memory spike. `iter_rows()` and `iter_query()` are the streaming counterparts: they wrap PyTables' `iterrows()` / `where()` generators, which read chunk-by-chunk from disk rather than building a full result array up front.

### `iter_rows(path, start=None, stop=None, condition=None) -> Iterator[Dict]`

Same parameters and same per-row normalization as `read_rows()`, but returns a generator instead of a list. Node resolution and condition compilation happen eagerly (the call itself raises immediately on a missing node or a bad condition string); only the per-row normalization is lazy.

```python
# Process a large table one row at a time without holding it all in memory.
for row in h5.iter_rows('/items'):
    process(row)

# Streaming also composes with start/stop and condition, exactly like read_rows().
for row in h5.iter_rows('/items', condition='price > 10.0'):
    process(row)
```

### `iter_query(path, condition, **kwargs) -> Iterator[Dict]`

Convenience wrapper around `iter_rows` that applies a condition string, mirroring `query()`'s relationship to `read_rows()`. Equivalent to `iter_rows(path, condition=condition)`.

```python
for row in h5.iter_query('/items', 'name == b"Widget"'):
    process(row)
```

**When to reach for streaming vs. the full-materialization methods:** if you need the whole result set as a Python list anyway (e.g. to sort it, count it, or pass it somewhere that expects a list), `read_rows()`/`query()` are simpler and no less efficient. Reach for `iter_rows()`/`iter_query()` when you only need to process rows one at a time, especially on tables large enough that materializing every match at once would be wasteful or risky.

<a id="indexing"></a>
## Indexing

By default, every condition-based operation (`read_rows(condition=...)`, `query()`, `iter_rows(condition=...)`, `iter_query()`, `remove_rows()`) resolves its matches with a full-table scan. `create_index()` wraps PyTables' fully-sorted (CSI) column index so those same operations can resolve against an index instead.

### `create_index(path, column, **kwargs) -> None`

Create a fully sorted index on `column`. Once created, **no other API call is needed to make use of it** -- index use by `read_rows`, `query`, `iter_rows`, `iter_query`, and `remove_rows` is inherited PyTables condition-evaluator behavior, not something tiferet-h5 special-cases or that a caller opts into per query.

```python
h5.create_index('/items', 'price')
```

Raises `H5_INDEX_FAILED` if `column` does not exist on the table, or if it is already indexed (the underlying PyTables error message points you at `reindex()` in that case).

### `is_indexed(path, column) -> bool`

Check whether `column` currently has an index.

```python
if not h5.is_indexed('/items', 'price'):
    h5.create_index('/items', 'price')
```

### `reindex(path, column=None) -> None`

Recompute an existing index after a batch of writes has invalidated it. **Re-indexing is always an explicit caller responsibility** -- it is never triggered automatically by `append_rows()` or `flush()`, since that would add unconditional cost to every write regardless of whether the table has any indexed columns at all.

```python
# Re-index one column after a bulk write.
h5.append_rows('/items', large_batch)
h5.reindex('/items', column='price')

# Or re-index every currently indexed column on the table at once.
h5.reindex('/items')
```

Calling `reindex(path, column=...)` on a column that was never indexed raises `H5_INDEX_FAILED` -- PyTables' own `Column.reindex()` silently no-ops in that case instead of raising, which `tiferet-h5` deliberately does not propagate as-is, since a silent no-op on a caller typo or bad assumption is exactly the kind of masked bug this package's error handling elsewhere goes out of its way to avoid.

## Array Operations

### `create_array(path, data, title='', filters=None) -> Any`

Create an array node at `path` from a NumPy array or Python sequence.  The parent group must already exist.  See [Compression](#compression) above for the `filters` parameter -- passing it creates a compressed `CArray` instead of a plain `Array`.

```python
import numpy as np
h5.create_group('/measurements')
h5.create_array('/measurements/temperatures', np.array([22.1, 23.4, 21.9]))
```

### `get_array(path) -> Any`

Retrieve the PyTables array object at `path`.

```python
arr = h5.get_array('/measurements/temperatures')
data = arr.read()  # returns NumPy array
```

## Attribute Operations

### `set_node_attr(path, name, value) -> None`

Set a single metadata attribute on the node at `path`.

```python
h5.set_node_attr('/features', 'schema_ver', '1.0')
```

### `get_node_attr(path, name) -> Any`

Retrieve a single attribute value.  Bytes are decoded to `str`; NumPy scalars are converted to Python natives.

```python
ver = h5.get_node_attr('/features', 'schema_ver')
# '1.0'  (plain Python str, not np.str_)
```

### `get_node_attrs(path) -> Dict[str, Any]`

Retrieve **all user-defined attributes** from the node as a plain Python dict.  System attributes managed by PyTables (`CLASS`, `TITLE`, `VERSION`, etc.) are excluded via `_v_attrnamesuser`.  Pass the result directly to `NodeObject.from_attrs()`.

```python
raw = h5.get_node_attrs('/features/calc')
# {'name': 'Calculator', 'desc': 'Arithmetic ops'}

group_obj = FeatureGroupObject.from_attrs(raw)
```

<a id="schema-integrity"></a>
## Schema Integrity

`_H5_TYPES` is a compile-time declaration; the on-disk table is whatever was actually created, potentially by an older version of the mapper class.  `TableObject.verify_schema()` ([docs/guides/mappers.md](../mappers.md#tableobject)) detects drift in both directions but never raises — it is a pure detector living in the mapper layer, which never imports `ServiceError`.  `H5Client.assert_schema()` is the enforcement half of that pair.

### `assert_schema(path, table_cls, check_version=True) -> None`

Verify the table at `path` against `table_cls`'s declared schema, raising `H5_SCHEMA_MISMATCH` when drift is detected.  **Enforcement is opt-in** — this is never called automatically by `get_table()` or `get_or_create_table()`, so existing callers are unaffected unless they explicitly ask for the check.  Opt-in was chosen deliberately over automatic enforcement: those two methods sit on the hot path of every table access, and silently raising on every call would be a breaking behavior change with real performance cost.

```python
with H5Client('data.h5', mode='r') as h5:
    h5.assert_schema('/features/calc/steps', FeatureStepObject)
```

When `check_version=True` (the default) and a `schema_version` node attribute is present on the table, it is additionally compared against `table_cls.schema_fingerprint()` — see below.  Pass `check_version=False` to check column drift only.

The mismatch list is attached to the raised `ServiceError` as `error.kwargs['mismatches']`.

### Schema Versioning

`TableObject.schema_fingerprint()` ([docs/guides/mappers.md](../mappers.md#tableobject)) returns a deterministic fingerprint derived from `_H5_TYPES`.  Stamp it as a `schema_version` attribute **on the table's own node** — not its parent group — right after creating the table:

```python
with H5Client('data.h5', mode='w') as h5:
    t = h5.create_table('/features/calc/steps', FeatureStepObject.get_description())
    h5.set_node_attr('/features/calc/steps', 'schema_version', FeatureStepObject.schema_fingerprint())
```

The marker lives on the table node itself, not the parent group, because a single group can hold multiple tables (see the nested-object pattern in [docs/guides/mappers.md](../mappers.md#nested-object-modeling)) — each needs independent versioning, and scoping the marker to the shared parent group would both conflate multiple tables' versions and collide with that group's own unrelated `NodeObject`-mapped attributes.

### Migration Pattern

PyTables tables are structurally fixed at creation — `tables.IsDescription` cannot be altered in place.  There is no in-place schema migration, and `tiferet-h5` does not ship a migration helper as of this alpha.  When a table's live schema needs to change, the documented pattern is a copy-and-rewrite:

```python
with H5Client('data.h5', mode='a') as h5:
    # 1. Read all existing rows under the old schema.
    old_rows = [OldStepObject.from_row(r) for r in h5.read_rows('/features/calc/steps')]

    # 2. Create the new table (new _H5_TYPES) at a temporary path.
    new_table = h5.create_table('/features/calc/steps_v2', NewStepObject.get_description())

    # 3. Re-write each row under the new schema.
    for old in old_rows:
        NewStepObject(**old.to_primitive()).to_row(new_table)
    new_table.flush()

    # 4. Remove the old table and move the new one into its place.
    h5.h5file.remove_node('/features/calc/steps')
    h5.h5file.rename_node('/features/calc/steps_v2', 'steps', '/features/calc')

    # 5. Stamp the new schema version on the table's new node.
    h5.set_node_attr('/features/calc/steps', 'schema_version', NewStepObject.schema_fingerprint())
```

A general-purpose migration engine with versioned upgrade chains is deliberately out of scope for this alpha — the pattern above is a starting point, not a shipped API.

<a id="concurrency"></a>
## Concurrency

`H5Client` (and, by extension, `H5Repository`/`TableRepository`/`NodeRepository`) makes **no concurrency guarantees beyond what PyTables/HDF5 itself provides.** HDF5 is fundamentally a single-writer file format:

- **Multiple readers, no writer:** safe. Any number of processes/threads may open the same file `'r'` concurrently.
- **One writer, no concurrent readers or other writers:** safe, and the only supported concurrent-write shape. A single `H5Client`/repository instance writing from one thread, with no other process or thread touching the same file at the same time, is the pattern every method on this page assumes.
- **One writer plus concurrent readers, or multiple concurrent writers:** **not safe.** PyTables performs no file locking of its own, and HDF5's own locking is unreliable across platforms/filesystems (notably NFS). Two processes writing to the same file at once -- or a writer and a reader overlapping -- can corrupt the file or produce a reader-visible inconsistent state, silently.

`tiferet-h5` ships **no lock helper** as of this alpha. This was a deliberate choice, not an oversight: no concurrent-writer usage pattern has actually surfaced in this codebase to date, and building a locking primitive speculatively risks exactly the kind of general-purpose concurrency machinery this package's RFP process has consistently ruled out of scope elsewhere (e.g. a migration engine, a query planner). If a real concurrent-access need emerges, a scoped file-lock wrapper around `H5Client`'s open/close lifecycle is a natural candidate for a future RFP -- not something to engineer in advance of an actual requirement.

**Practical guidance for a single process today:**

```python
# Safe: sequential access via short-lived context managers -- this is the
# pattern every method on this page already assumes.
with H5Client('data.h5', mode='a') as h5:
    h5.append_rows('/items', new_rows)

with H5Client('data.h5', mode='r') as h5:
    rows = h5.read_rows('/items')
```

If your application needs multiple threads or processes touching the same file, serialize access yourself (e.g. a single writer thread/process that owns the file, with others communicating through it) rather than relying on any implicit safety from `tiferet-h5` or PyTables.

## Error handling

Every `H5Client` failure surfaces as a `ServiceError` (`tiferet.interfaces`), never a `TiferetError`. A `ServiceError` is deliberately **not** a `TiferetError`: an HDF5/PyTables failure is infrastructural, not a domain outcome, so it is never resolved through an error catalog and never formatted into an API response — it surfaces as an unhandled exception, which is the intended behaviour. It is also not skippable via a feature step's `pass_on_error`, which passes on domain errors only.

Codes are hosted in `tiferet_h5/utils/h5.py` beside the raise sites (there is no longer a dedicated `assets` catalog module):

```python
from tiferet.interfaces import ServiceError
from tiferet_h5.utils.h5 import (
    H5_FILE_NOT_FOUND_ID,          # file absent (read) or parent dir absent (write/append); also a low-level open failure
    H5_INVALID_FILE_ID,            # missing .h5 / .hdf5 extension in a read mode
    H5_INVALID_MODE_ID,            # mode not one of r / r+ / w / w- / a
    H5_FILE_ALREADY_OPEN_ID,       # open_file() called when the handle is already open
    H5_CONN_NOT_INITIALIZED_ID,    # any operation attempted before open_file()
    H5_NODE_NOT_FOUND_ID,          # path does not exist in the open file
    H5_GROUP_CREATE_FAILED_ID,     # create_group() (or an intermediate parent) raised a PyTables exception
    H5_TABLE_CREATE_FAILED_ID,     # create_table() raised a PyTables exception
    H5_QUERY_FAILED_ID,            # read_rows() / query() raised a PyTables exception
    H5_WRITE_FAILED_ID,            # append_rows(), remove_rows(), or create_array() failed
    H5_SCHEMA_MISMATCH_ID,         # assert_schema() detected column or version drift
    H5_INDEX_FAILED_ID,            # create_index() / reindex() failed (unknown column, already indexed, or not yet indexed)
    H5_COMPACT_FAILED_ID,          # compact() failed during the copy or the atomic file replacement
)
```

**Catches are narrowed to specific PyTables/stdlib exceptions**, not a bare `except Exception`, so a bug unrelated to HDF5 I/O (e.g. a programming error inside a caller's callback) is never mislabeled as an infra error:

```python
try:
    with H5('data.h5', mode='a') as h5:
        h5.append_rows('/items', [{'unknown_col': 1}])
except ServiceError as e:
    if e.error_code == H5_WRITE_FAILED_ID:
        print('Underlying driver failure:', e.__cause__)  # KeyError('no such column: ...')
    raise
```

## Boundaries

**Inside this domain:** the HDF5 file lifecycle, group/table/array/attribute operations, the PyTables-exception-to-`ServiceError` wrapping (with cause chaining), opt-in schema drift enforcement via `assert_schema()`, memory-safe row streaming via `iter_rows()`/`iter_query()`, column indexing via `create_index()`/`is_indexed()`/`reindex()`, per-call compression via `filters` on `create_table()`/`get_or_create_table()`/`create_array()`, and file compaction via `compact()`.
**Outside this domain:** the inherited file/path handling ([docs/core/utils.md](https://github.com/greatstrength/tiferet/blob/main/docs/core/utils.md) — `FileLoader`); a general-purpose schema migration engine with versioned upgrade chains (a documented copy-rewrite pattern is all this alpha ships); a concurrent-write lock helper (documented as a known gap above, deferred to a future RFP if a real need emerges); domain-object persistence via a repository ([docs/guides/repos.md](../repos.md) — `TableRepository`/`NodeRepository`, `tiferet_h5/repos/core.py`, including the repository-level compression default).

See [examples/catalog_app](../../../examples/catalog_app) for a runnable, end-to-end demonstration of this layer working together with the mapper and repos layers.
